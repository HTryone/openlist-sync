# 备选方案：单向 sync + copy 预取（bisync 不稳时）

如果 bisync 在真实弱网下不稳定（频繁中断、老要 resync），退回这套更简单可控的方案。

## 思路

```
写侧（本地 -> OpenList）：rclone sync     单向备份，含删除传播 + 垃圾桶归档
读侧（OpenList 共享 -> 本地缓存）：rclone copy   显式预取，只增量拉，不删本地
```

与 bisync 的差别：

| | bisync | 单向 sync + copy |
|---|---|---|
| 同步方向 | 双向 | 写单向、读单向 |
| 删除语义 | 双向传播 | 只写侧传播删除；读侧 cache 不因远端删除而删 |
| 冲突 | 生成 conflict 副本 | 写侧以本地为准覆盖；读侧不改远端 |
| 弱网鲁棒性 | 中断可能需 resync | 每次幂等，失败重跑无副作用 |
| 透明性 | 本地=完全镜像 | 读侧是"缓存"，需显式 pull |

## 命令（即 [deploy/openlist-fallback.sh](../deploy/openlist-fallback.sh)，已实测 5/5）

```bash
# 写侧：本地工作区 -> OpenList，删除归档到目标之外的 .trash
rclone sync /work/workspace openlist:/ty2/agents-sy/workspace \
  --backup-dir openlist:/ty2/agents-sy/.trash/workspace \
  --checksum --max-delete 50 \
  --retries 10 --low-level-retries 20 --contimeout 30s --timeout 5m

# 读侧：共享目录预取到本地缓存
rclone copy openlist:/shared/docs /work/_cache/shared \
  --checksum --retries 5 --timeout 3m
```

> 注意：单向 `rclone sync` 用 `--backup-dir`（单数）；`--backup-dir1/2` 仅 bisync 用。
> 这点已踩过坑，脚本里已修正。

## 部署

```bash
./openlist-fallback.sh          # 推 + 拉全流程
./openlist-fallback.sh push     # 只推
./openlist-fallback.sh pull     # 只拉
```

cron（每 30 分钟推、每小时拉，按需调）：

```cron
*/30 * * * * root /usr/local/bin/openlist-fallback.sh push >> /var/log/openlist-sync.log 2>&1
0    * * * * root /usr/local/bin/openlist-fallback.sh pull >> /var/log/openlist-sync.log 2>&1
```

## 目录布局（fallback 版）

```
本地：
  /work/workspace/        # 写侧源
  /work/_cache/shared/    # 读侧缓存（远端共享目录的本地副本）
  /work/.trash_local/     # （可选）本地删除留档

OpenList：
  /ty2/agents-sy/workspace/        # 写侧目标（与本地镜像）
  /ty2/agents-sy/.trash/workspace/ # 写侧删除归档（目标之外，各自独立）
  /shared/docs/                    # 读侧共享源
```

## 何时用哪套

- **日常首选 bisync**：语义最贴合"坚果云"，双向透明。
- **满足以下任一就切 fallback**：
  - bisync 经常中断、频繁要求 `--resync`
  - 网络极不稳定，无法承受全量重扫
  - 只需要"备份 + 偶尔取共享文件"，不需要严格双向镜像
